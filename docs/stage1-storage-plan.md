# Этап 1: совместимое расширение наблюдений и безопасный откат

Статус: реализовано и проверено в сборке `stage1-08cb8dae8709`, 18.11.2026. Ниже сохранён совместимый план хранения и отката, использованный при реализации общего вспомогательного модуля. Работа выполнена только в `/workspace/math-stage1-dev`; исходная копия P0, production и данные ребёнка не изменены.

## Владельцы данных

Существующие ключи `kubiki-progress-v1`, `detalki-progress-v1` и `slovograd-v1` сохраняются. Старые достижения, снимки, ID уроков, scoped completions и черновики остаются в прежних полях. В каждом объекте добавляется необязательное поле `learning` версии 1. Четвёртого общего ключа прогресса нет. Старый результат без наблюдения имеет статус «не проверено»; он не превращается в самостоятельное освоение.

`learning` содержит `generation`, до 240 наблюдений и один снимок новой активности. Наблюдение связывает стабильный taskId/skillIds, attemptId/eventId, вариант и редакции, первоначальный/окончательный исход, флаги объяснения, визуальной помощи, ошибки и готового решения. Не сохраняются голос, полный чат, координаты жестов или свободные персональные высказывания. Внешние версии неизвестного формата не понижаются до версии 1.

Снимок `activity` имеет `revision`, `updatedAt`, `ownerId` и ограниченный JSON `state` (до 48 KiB); предметный интерфейс отдельно проверяет разряды, диапазон, ID и допустимость восстановления. Это новый вид активности внутри существующего владельца, а не копия старой доски. Между вкладками наблюдения объединяются по eventId; одно событие с исправлением содержит накопленные факты помощи.

## Поколение сброса и вкладки

Поколение `learning.generation` должно соответствовать `resetEpoch` владельца. При merge разных поколений последняя прочитанная запись хранилища считается авторитетной; события прежнего поколения не возвращаются. При явном reset приложение создаёт новый resetEpoch и пустое learning с этим поколением. Новые действия после сброса относятся только к новому поколению.

Вспомогательный модуль не пишет localStorage и не объявляет его транзакционным. Приложение обязано перед записью прочитать последнюю запись, не перезаписывать чужой активный черновик пассивной вкладкой и принимать storage-события. При конфликте активного занятия предпочтительна одна активная вкладка с явным уведомлением. Одно только слияние массивов не доказывает отсутствие гонок read-modify-write; интерфейсные проверки нескольких вкладок обязательны.

Старая вкладка с кодом до этапа 1 не знает поля learning и может удалить его полной записью. Выпуск не использует forced reload: новые записи включаются после завершения обновления и закрытия старых клиентов. При ручной приёмке проверяются старый worker/new waiting, открытая задача и повторный запуск. Автоматическое согласование с произвольным старым writer не обещается.

## Ограничения и отказ записи

Невалидный или слишком большой объект не получает новых автоматических достижений. Неизвестная версия `learning` остаётся непрозрачной и не перезаписывается helper-модулем. Ошибка чтения/загрузки не разрешает записать пустой объект поверх исходного raw JSON. При квоте приложение сохраняет прежнюю запись и сообщает об ограничении; модуль не удаляет историю автоматически из других полей.

Ограничение истории не удаляет последние наблюдения навыков без необходимости: сохраняются последние события, приоритетно покрывающие разные skillIds, затем остальные последние. Это история наблюдений, не готовый вывод об устойчивом освоении. Старые галочки не меняются при сжатии.
